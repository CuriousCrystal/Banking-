AMC Bank — BFSI Full-Stack Banking Application

8-Day Project Report · Tools & Technologies · Presentation Speech

Java Full-Stack Training Project · September 21–30, 2026

1. The Project in One Paragraph

We built AMC Bank, a working internet-banking back office: a Spring Boot REST API secured with JWT login and role-based access (Admin / Officer / Clerk), backed by a MySQL database, and a React dashboard that shows live figures — customers, accounts, loans and deposits — with charts. Every endpoint was tested in Postman, and the whole stack runs end-to-end on one machine (verified September 30: backend on port 8080, frontend on port 5173).

4. Presentation Speech (≈ 4 minutes)

Good morning everyone. Over the last eight days I built AMC Bank — a full-stack banking application — and I'd like to walk you through what we did, the tools we used, and what I learned.

Where we started. Day one wasn't code — it was foundations. I installed and verified the entire toolchain: Java, Maven, MySQL as a Windows service, Eclipse with Spring Tools, Postman and Git. From the very first commit, every day's work is visible in version control — a discipline I kept all through the project.

Core Java first. Before touching Spring, I revised collections the practical way: an ArrayList as a passbook, a HashMap for balances, a HashSet to catch duplicate PANs, a Queue for cheque processing — plus generics and the full exception family. That paid off immediately, because banking code is mostly data structures and edge cases.

Then the API. We designed the REST contract in Postman before writing controllers — request, response, status codes. The backend is Spring Boot with three layers: controllers that speak HTTP, services that enforce the business rules — like blocking a withdrawal that overdraws an account — and Spring Data repositories that talk to MySQL through JPA entities. One customer can hold many accounts and loans, handled with proper cascades.

Security was the deepest day. The API is stateless and token-based: you log in, Spring Security verifies BCrypt-hashed passwords and issues a JWT; every request passes through a filter that validates the token. Access is role-based — Admin can delete and manage users, Officers sanction loans, Clerks can read and create but not delete. Wrong password gets a clean 401; right token but wrong role gets a 403 — all in a uniform JSON error shape the frontend understands.

The frontend is a React single-page app built with Vite: a login screen, a dashboard with live figures and two charts, and full screens for customers, accounts, loans and users. An Axios interceptor attaches the token to every call and reacts automatically when a session expires.

How it was verified. Every endpoint was tested in Postman — happy paths and error paths. On the final day I integrated everything end-to-end on real MySQL: seeded demo data, logged in through the UI, watched the dashboard pull live numbers — eleven customers, fourteen accounts, nine active loans — and confirmed the security boundaries behave exactly as designed.

What I take away: how the pieces actually fit — HTTP → controller → service → repository → database and back; why security belongs in a filter chain, not sprinkled through the code; and how a frontend and backend negotiate through a clear API contract. Everything you saw today is running live on this machine — thank you, and I'm happy to take questions.
